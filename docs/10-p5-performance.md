# P5 · 百万字级性能：增量扫描缓存

> 这一期只做一件事：让「百万字工程」不再每次请求重扫全书。
> 数字全部来自可复跑的基准脚本；本文件记录**怎么量的、改了什么、为什么不做另外那两件事**。
>
> **这份文档被我自己推翻过一次。** 第一版的数字（10–14×）来自一个不够真实的文件系统替身，后来在真实实例上量才发现对不上。§1.3 完整记录了这次翻车——它是这一期最有价值的部分。

---

## 1. 先量，再改

### 1.1 尺子本身要合格

`06` §2.1 与 `07` §5 都记着同一个取舍：检索语料与检查语料**每次请求从磁盘重扫**，换来「答案来自磁盘现在的内容」这个承诺；两处都写明 P5 要把它变成增量。

于是第一步不是改代码，是造一把尺子。`spike/perf-check.mjs` 写一本**合成的百万字书**：每章 3000 字、50 章一卷，正文由固定种子的伪随机从词池里拼出来（两次跑读到同样的字节），frontmatter 与 `03` 的章节格式一致，另有 8 张角色卡、8 张地点卡、10 张伏笔卡、每卷一份卷纲。

关键在**文件系统替身必须是真磁盘，而且要照抄 `dsh-fs-local` 的每一次系统调用**。脚本用 `node:fs` 实现 `ctx.fs` 这一层，并且：

- `resolve` 做 **`realpath`**（缺失路径时按 `resolveLocalTarget` 的祖先回退规则拼回去）；
- `listDir` 对**每个子项**先 `realpath` 再 `stat(bigint)`（`resolveListedChildTarget` + `probe`）；
- `readText` 读之前先 `stat` 一次（`fsio` 的 raw-read stat preflight）；
- 版本令牌用 `dev:ino:size:mtimeNs:ctimeNs`，目录列举里给每个子项带上。

用内存替身量这件事是**在量错的东西**；而漏掉 `realpath` 是同一个错误的更隐蔽版本——见 §1.3。

### 1.2 改动前的基线（400 章 / 124.5 万字）

```
snapshot 第 1 次（冷）    545 ms   listDir 117 · stat 19 · resolve 201 · readText 140 ms ×401
snapshot 第 2 次          543 ms   （与冷启动几乎一样：完全没有复用）
search「墨尘」            599 ms   listDir 123 · stat 21 · resolve 230 · readText 156 ms ×436
check                    594 ms   listDir 135 · stat 21 · resolve 223 · readText 156 ms ×436
```

**第 2 次和第 1 次一样慢**，这就是问题本身：每次请求都在重新读、重新解析、重新算字数。

拆开看，钱花在三个完全不同的地方——所以有三种完全不同的修法，不拆开就只能猜：

| 花在哪 | 每次请求 | 说明 |
|---|---|---|
| `readText` | ~150 ms | 400 个文件的读取（含 fs-local 的 stat 前置检查） |
| `resolve` | ~220 ms | 每个路径一次 `realpath`（插件每个文件解析两次） |
| `listDir` | ~120 ms | 每个子项一次 `realpath` + 一次 `stat` |
| 其余 | ~100 ms | YAML 解析、字数统计、n-gram 匹配 |

而**直觉上最像瓶颈的那部分——`searchDocs` 对全文做 n-gram 匹配——只占很小一块**。如果照直觉去写倒排索引，会优化掉最小的一份。

### 1.3 一次被真实实例抓住的测量错误

第一版的替身里，`resolve` 是 `path.resolve`、`listDir` 只做 `readdir + stat`。那一版量出来是：

```
search 第 2 次   227 ms（其中 readText 132 ms）
snapshot 第 2 次 215 ms
```

于是第一版文档写下了「**10–14×**」。这个结论是错的。把它放到真实实例上（隔离 profile + `spike/perf-check.mjs` 造的那本书）量，同一批操作是：

```
/api/novel/ping     8 ms      ← 空转的底噪
/api/novel/project  330 ms    ← 快照
/api/novel/search   380 ms
/api/novel/checks   412 ms
```

**每一条都比替身慢 3–9 倍，而且慢的比例各不相同。** 差在哪，`spike/fs-cost-check.mjs` 给了答案：

```
20 个目录 / 1000 个文件
readdir，不算子项                               4 ms
readdir + 每子项 stat(bigint)                36 ms
readdir + 每子项 realpath                   230 ms
readdir + realpath + stat（fs-local 的做法）   272 ms
→ 每文件约 0.27 ms；realpath 是主要那一项
```

`dsh-fs-local` 为了给出「跨符号链接稳定的 target key」，**对列举里的每一个子项都做一次 `realpath`**——在 Windows 上，一次 `realpath` 约等于八次 `stat`。替身把这一步省了，于是把**唯一在冷缓存下仍然存在的那项成本**抹掉了。

补上 `realpath` 之后，替身的数字与真实实例对上了（1000 章：替身 1453 ms 冷 / 340 ms 暖，真实 HTTP 1688 ms 冷 / 330 ms 暖）。**尺子校准之后，下面的数字才是数字。**

> 这一条后来变成了 `README` 的第 6 条教训的近亲：替身也是代码，它错的时候会以「产品做对了」的样子报出来。这次的形态更阴——它没有报错，只是**安静地把最重要的成本算成了零**。

## 2. 改了什么

### 2.1 一个只缓存字节、不缓存判断的缓存

新增 `src/novel/cache.ts`（`ProjectCache`），一个进程内的**穿透式缓存（read-through cache）**：

- 缓存的是**一个文件的字节与那份字节的解析**：原文、frontmatter、正文，以及一个「只由这个文件自己决定」的派生值。
- **不缓存任何关于工程的判断。** 每次扫描照旧列出目录、逐个比对新鲜度令牌；令牌变了就重读重解析。只有令牌与上次解析时**逐字节相同**的文件才复用。

这就是为什么「答案来自磁盘现在的内容」这句承诺没有被吃掉：**在外部编辑器里改了一章，下一次请求就看得见**，因为发现变化靠的是令牌比对，而不是靠「这个文件我们见过」。这条承诺有断言，也在真实实例上验过（§4.2）。

令牌用的是 `dsh-fs-local` 自己那套 `dev:ino:size:mtimeNs:ctimeNs`——同一毫秒内两次写入也会变（DSH 有测试专门钉这一点），这正是它的守护式写入所依赖的东西。

### 2.2 令牌从哪来：目录列举里免费的

`dsh-fs-local` 的 `listDir` 已经为每个子项 `probe` 过一次，返回值里**本来就带 `version`**。插件的 `FsDirEntry` 之前把这个字段丢掉了，现在接上：

- 有令牌 → 直接用，**一次额外 stat 都不用**；
- 没有（别的后端）→ 退回 `stat` 取令牌；
- `stat` 也没有 → **不缓存，每次照读**。

第三条是刻意的：宁可退化回旧行为，也不拿一个无法校验的新鲜度去骗自己。

### 2.3 缓存的值必须是「只由这个文件决定」的

这条约束是整个设计里最容易写错的地方。派生值（`Derive<T>`）只允许依赖它拿到的那个文件，因为**它被缓存的依据只有那个文件的令牌**。

设定卡正好有个反例：`appearsIn`（这张卡被哪些章引用）来自**章节**，不是来自卡。所以：

- `summarizeCard` 拆成 `summarizeParsedCard`（只算卡自己的部分，可缓存）+ 调用方叠加 `appearsIn`（每次现算）；
- 于是「改一章的 `characters` 字段」会立刻反映到卡的 `appearsIn` 上，**哪怕卡自己的令牌一动没动**。`format-check` 专门为这件事留了一条断言。

顺带这也去掉了一次重复解析：卡片以前是「扫描时解析一遍、`summarizeCard` 里再解析一遍」。

### 2.4 面板自己写的那一下，不等令牌

`NovelIo.write` 成功后立刻 `cache.invalidate(root, path)`。真实后端上令牌本来就会变，但**我们自己写的文件是我们确切知道变了的东西**，没必要再去比对一个可能不够强的令牌。

### 2.5 其它

- 扫描分组成 `chapters` / `cards` / `pages`，各自只清理自己上次见过的路径——否则扫卡片会把章节缓存全踢掉。
- 缓存按 `scope.root` 分家，同名文件在两个工程之间不串。
- 单文件页（world / timeline / book / 卷纲 / 文风）也走同一个缓存，保证整份语料来自同一个视图。

### 2.6 一处对格式真源的偏差：没有 `.novel/index.json`

`03` §5（以及需求 §6 的架构表）写的是「倒排索引、别名表 → `.novel/index.json`，文件变更时增量更新」。本期**没有落这个文件**，索引活在宿主进程的内存里。理由有三条，都已回写 `03`：

1. **冷启动只要一次。** 百万字的冷扫描是半秒级（400 章 / 124.5 万字实测 545 ms），而一个插件实例的生命周期就是一次宿主进程。把它存到磁盘，换来的是「下次开进程省半秒」。
2. **落盘要付写入代价。** 一个几 MB 的 JSON 在每次保存章节时重写，成本高于它省下的读取；而它一旦过期，就是磁盘上第二个可以撒谎的真相。
3. **内存副本不会过期到没人发现。** 进程内的缓存随进程消失，不存在「昨天的索引文件还在」这种状态。

格式真源因此改了：`.novel/` 里只剩 `history/`、`checks.json`、`runs/`（都进 git）；索引不进 `.novel/`，因为它根本不是一个文件。

## 3. 改动后

### 3.1 一百万字的规模（400 章 / 124.5 万字）

```
snapshot   冷 545 ms  →  暖 122 ms     4.5×
search     冷 599 ms  →  暖 138 ms     4.3×
check      冷 594 ms  →  暖 139 ms     4.3×
```

冷的那一次**没有变慢**：缓存不引入额外的读，只是把结果留下。

### 3.2 三百万字（1000 章 / 311 万字）

```
snapshot   冷 1340 ms  →  暖 296 ms    4.5×
search     冷 1453 ms  →  暖 340 ms    4.3×
check      冷 1391 ms  →  暖 345 ms    4.0×
```

「改动前」的那一行不是回忆录，是脚本当场量的：**每次新建一个 `NovelIo`（缓存为空）等价于旧代码的全量重扫**，所以对照在同一次运行里跑出来，不依赖我留着旧代码。

### 3.3 剩下的时间花在哪——以及为什么不做倒排索引

400 章暖检索的 138 ms：

| 部分 | 耗时 | 说明 |
|---|---|---|
| **目录列举**（9 个目录 / 400 个文件） | **~120 ms** | 新鲜度的底线：不看一眼就不可能知道文件变没变。其中绝大部分是 `dsh-fs-local` 每个子项一次 `realpath`（§1.3） |
| 重建语料对象 | ~2 ms | 一千来个对象，便宜到不值得缓存 |
| 全文 n-gram 匹配 | ~12 ms | 全文的 `toLowerCase` + `indexOf` |

**这就是不做倒排索引的理由，而且是一个有数字的理由**：真正能被倒排索引拿掉的只有那 12 ms，占暖检索的 8%，而占 87% 的列举它一点都碰不到。在一本三百万字的书上花复杂度去优化 12 ms，同时留下「位置与片段必须与 n-gram 语义逐字一致」的一致性风险，是一笔坏买卖。`03` §5 的「倒排索引」一行因此改成了「扫描缓存」，并写明了这个取舍。

### 3.4 一个看起来显然、但被证据否掉的优化

既然列举是唯一的剩余成本，而列举的代价是「每个子项一次 `realpath`」，最自然的想法是：**目录自己的令牌不是也能当新鲜度吗？** 如果目录令牌没变，说明没有增删文件，就跳过列举；有变动再列。

`spike/fs-cost-check.mjs` 把这条路堵死了：

```
20 轮新增/删除（立刻读，第一次跑）：新增后令牌变了 8 次，删除后变了 10 次
20 轮新增/删除（立刻读，第二次跑）：新增后令牌变了 3 次，删除后变了 15 次
20 轮新增/删除（等 10 ms 再读）：新增后令牌变了 19–20 次，删除后变了 20 次
只改子项内容后目录令牌变化：false
```

也就是说：**目录令牌最终会动，但不是立刻动**（NTFS 的目录元数据更新是延迟落地的）。而插件遇到的恰恰是「刚保存完一章就刷新工程树」这种立刻读的场景——20 次里有 12–17 次会读到没变的令牌，于是**新章在树里消失**。

两次运行的即时读数还不一样（8/10 与 3/15）。这本身就是结论：**它不是「弱信号」，是「不确定的信号」**，而不确定的信号不能用来守正确性。所以这条优化不做，并且把「为什么不做」钉在了脚本输出里。

如果只看第一次实验（单次采样读出 `false`）或者只看延迟后的结果（`true`），都会得出相反的结论。**一个不确定的信号不能用来守正确性**，所以这条优化不做，并且把「为什么不做」钉在了脚本输出里。

> 这一段是本轮第二个被真实输出打脸的地方。第一次跑 `fs-cost-check` 打印的是「新增 `true` / 重命名 `false`」，隔一次再跑同样代码打印的是「新增 `false` / 重命名 `true`」——单次采样得不出结论，只能记速率。这和 M5 那条教训是同一件事的不同形态（`README` 教训 5）：**先跑一遍，再写下「所以」。**

## 4. 怎么验的

### 4.1 检查脚本（`spike/format-check.mjs`，本节新增 9 条）

| 断言 | 防的是什么 |
|---|---|
| 再检索一次不重读任何正文 | 缓存根本没生效（最蠢也最可能的那种回归） |
| 暖扫描连章节文件的 `stat` 都不用 | 「令牌由列举免费给出」这条被悄悄退化回逐个 `stat` |
| 面板刚保存的那一章下一次检索就看得见 | `invalidate` 忘了写（缓存吃掉自己的写入） |
| 面板之外改的文件（新令牌）也看得见 | 只信「我们见过的文件」，外部编辑看不见 |
| 旧正文不会因为缓存留在结果里 | 复用陈旧解析 |
| 卡片的反向链接跟着章节走 | 把「依赖别人的派生值」也缓存了——最隐蔽的一类 |
| 文件在面板外被删掉后不再出现在树里 | 只增不减的缓存：删掉的章还在答 |
| 后端不给版本号时宁可每次重读 | 拿一个不会变的令牌当新鲜度 |
| 同名文件在两个工程之间不串 | 缓存没有按工程根分家 |

复现方式：`memoryFs({ listVersion })` 这个替身可以在「列举带令牌 / 不带令牌 / `stat` 也不带令牌」三种后端之间切换，所以上面三种降级路径都是**真跑过**的，不是推理出来的。

> **写这段代码时被抓出来的一个真 bug**：第一版的 `scan` 在「哪里都拿不到令牌」时直接 `continue`，也就是**根本不读这个文件**——不是「不缓存」，是「当成不存在」。`format-check` 那条「宁可每次重读」的断言当场变红。降级路径必须写测试，否则降级就是静默丢数据。

### 4.2 真实实例（HTTP，1000 章 / 311 万字）

在隔离实例上（`.dsh-home` + `DSH_NOVEL_ROOT=.spike-novel-perf`）对着**真 `ctx.fs`** 跑：

```
/api/novel/ping          8    8   15 ms
/api/novel/project     348  320  330 ms    ← 快照，暖
/api/novel/cards       348  329  331 ms
/api/novel/search      362  396  377 ms
/api/novel/checks      425  409  412 ms
```

- 空转底噪（`ping`）只有 8 ms，所以上面这些数字几乎全是扫描成本。
- 第 1 次 `search` 是 1688 ms，第 2、3 次是 380 ms 上下：**4.4×**，且第 2 次与第 3 次一致（稳态）。
- 这一组数字与校准后的替身（1453 → 340 ms）在同一量级，替身可信。

**缓存承诺的核心那一条**，也在真实实例上走完了（走 HTTP，绕过面板直接改文件）：

```
改动前 search「照夜白驹」命中 0 条
面板外写入后        命中 1 条  →  chapters/v01/c0001.md
  片段：…风从山口灌进来，带着铁锈与雪的味道。 照夜白驹衔着一枚断齿铜扣。
改回原样后          命中 0 条（应为 0）
```

也就是说：**在插件之外改一章，下一次请求就看得见；改回去，也立刻看不见。** 缓存没有把旧正文留在内存里。这一条走的是真 `ctx.fs`、真 `dsh-fs-local` 的令牌，而不是替身。

### 4.3 真实 GUI 验证清单（需要作者点）

性能改的是内部实现，面板不该有任何可见变化——所以这一节验的是**没有变化**：

- [ ] 打开一个工程，章节树照常出现（第 2 次打开明显更快）。
- [ ] 检索一个角色名，答案、依据、命中片段与改动前一致。
- [ ] 跑一次一致性检查，报告条目数与改动前一致。
- [ ] **在 DSH 之外**（VSCode / 记事本）改一章正文再保存，回到面板立刻检索那句新话——应当命中。这一条是缓存承诺的核心。
- [ ] 同样地，在外部改一张卡的 `name`，检索新名字应当命中。
- [ ] 在外部删掉一章的 md 文件，工程树里它应当消失（刷新工程树）。
- [ ] 保存一章后立刻检索刚写的句子，应当命中（不应出现「刚写的东西搜不到」）。
- [ ] 在一个大工程（几百章）里连续切换页签，每一步都应当是「立刻」而不是「卡一下」。

## 5. 已知欠账（本期不做）

- **暖扫描仍是 O(文件数)，而且瓶颈不在插件里。** 400 章约 120 ms、1000 章约 300 ms，几乎全是 `dsh-fs-local` 列举时每个子项一次 `realpath`。插件的能力面里没有更便宜的列举原语，目录令牌又不能用来跳过列举（§3.4）。**要真正解决，只有两条路**：DSH 侧让列举免掉不必需的 `realpath`（或提供只返回名字+令牌的轻量列举），或者引入文件变更通知（需求 §6 提过 `workspaceFiles.changes`，**DSH 侧是否可用我没验证**，不写成结论）。两条都不在插件里能做完。
- **内存占用随书增长。** 缓存持有每章的原文与正文（正文多半是切片，共享缓冲区），300 万字约十几 MB。没有做上限或淘汰：一个作者不会同时开着十本百万字的书，做 LRU 是为不存在的问题增加状态。
- **并发**：两个请求可能同时扫描同一个工程，各自读一遍再各自写入缓存。结果一致（幂等），没有加锁。
- **倒排索引**：见 §3.3，本期有意不做。
- P5 的其余部分（导出、快捷键、错误处理）仍 ⬜。
