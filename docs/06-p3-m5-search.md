## 1. 这一期做了什么

需求 M5 要的三件事是**问答**，不是搜索框：

| 问法 | 答什么 | 依据 |
|---|---|---|
| 「某人上次出场在哪」 | 最近一章 + 全书出现章数 | 章节 frontmatter 的 `pov`/`characters`/`locations` 反查 |
| 「某物品第一次出现是哪章」 | 最早一章 | 卡片 `firstAppear` 与反查相互对照；没有卡时按关键词命中 |
| 「某设定在哪解释过」 | 卡片路径 + 正文里最早提到它的章 | 卡片文件本身 + 正文关键词 |

D11 定的是「结构化反查 + 摘要 + 关键词，不引入向量库」。这一期把它按字面做完：**没有任何模型调用、没有 embedding、没有新落盘**，答案全部由磁盘上的文件当场推导。它同时是 M6 确定性检查的地基——`search.ts` 里的实体解析、别名展开、伏笔生命周期、`firstAppear` 与实测的对照，M6 会直接用。

### 1.2 新增路由

| 路由 | 方法 | 用途 |
|---|---|---|
| `/api/novel/search` | GET | `q` = 原样的问题或关键词，`limit` 可选（默认 40，上限 200）。空 `q` 返回 `empty:true` 的空结果，不是错误 |

### 1.3 一个答案必须说明它是哪一层的事实

同一条事实在工程里可能同时存在于三处，而它们会不一致。这一期的规矩是**分层陈述，不替作者裁决**：

- **卡片自己的字段**：`settings/characters/chen-mo.md · 卡片 frontmatter（角色）`；
- **章节 frontmatter 的登记**：`chapters/v01/c0003.md · frontmatter characters 含 chen-mo`；
- **正文的字面命中**：`chapters/v01/c0001.md · 关键词命中「青铜镜」`。

所以答案长这样（真实实例跑出来的原文）：

```
角色「陈默」最近一次出场：第 3 章《第三章 青铜镜》（按章节 frontmatter 的出场登记）。全书只有这一章登记了它。
```

而「第一次出场」问到时，卡片里的 `firstAppear` 会与实际反查结果**对照**：

```
角色「陈默」第一次出场：第 1 章《楔子·雨夜》（按章节 frontmatter 的出场登记）。…（卡片里写着 firstAppear: c0001，与最早的出场登记一致。）
```

不一致时说的是：

```
注意：卡片里写着 firstAppear: c0005（第 5 章《…》），与最早的出场登记不一致。
```

这一条不是锦上添花：`firstAppear` 是手写的，章节的 `characters` 是任务写的，两者漂移是长篇写作里最容易发生也最难自己发现的事。M6 会把它升级成正式的一致性检查，M5 先把话说清楚。

### 1.4 中文没有分词器，所以命中一定带原文片段

插件不引入分词依赖，一个中文句子进不来词表。规则是：

1. **疑问词先整段剥掉**（「上次」「在哪里」「第几次」「解释过」……按长度从长到短替换成空格），剩下的才是检索词；
2. **剩下的词条按重叠的 2–4 字 n-gram 匹配**，同一起点取最长命中，越长的 n-gram 权重越高（`size²`），单个文档的正文得分封顶 600（长章节不能因为长就压过精确命中）；
3. **只剩一个虚词的碎片不算词条**（「出现了几次」剥完只剩「了」，那不是词）；
4. **实体名与别名按全字匹配**，不参与 n-gram——名字是精确的东西。

这是近似算法，所以**每条命中都带它命中的那段原文**，匹配到的位置原样高亮。排序可以错，但作者一眼能看出它为什么排在那里。

### 1.5 面板：答案在前，证据在后

`SearchView` 的读法就是上面那条规矩的界面版本：

```
[问题框]  [检索]  [清空]
识别到：陈默 · 默哥          ← 点一下跳到设定页并打开这张卡
┌ 答案（一句话 + 可点的章节按钮 + 可展开的「依据 N 条」）
├ 命中列表：第 3 章 裂纹 · 出场角色登记、正文
│           灯下，青铜镜的裂纹又深了一分。陈默想起老周说过的话……   [跳到正文]
└ 扫描 8 个文件 · 章节命中 1 · 设定卡 0 · 文档 0
```

没有一个结果是没有出处的，也没有一次点击是死路：章节跳到正文页，设定卡与文档切到设定页打开对应文件。

## 2. 四个需要记录的决定

### 2.1 语料每次请求重扫，不做缓存

`searchCorpus` 每次都重新读章节与卡片。代价是明显的（P5 要做百万字级性能时这里必然是第一个瓶颈），换来的是**「答案来自磁盘现在的内容」这个承诺**——一次检索的结果和刚保存的那一章之间不能有窗口期。缓存要等 P5 连同增量索引一起做，而不是现在先加一个会撒谎的。

> **P5 已实现（2026-09-12，`10-p5-performance.md`）。** 这一节的取舍兑现了：`searchCorpus` 现在从 `src/novel/cache.ts` 的扫描缓存上重建，缓存**字节与解析**、不缓存判断，每次扫描照旧列目录比对新鲜度令牌，所以上面那句承诺原样成立。实测 1000 章 / 311 万字：检索 1453 ms → 340 ms（4.3×）。原文保留，作为当时的决定记录。

### 2.2 没有卡的东西也要能回答

需求举的例子是「某物品第一次出现是哪章」，而作者往往**还没有为它建卡**（青铜镜就是先出现在正文里）。第一版实现只对能解析成卡片的实体作答，于是这个问题完全没有答案。现在补了一条：没有实体但问的是「第一次/最近一次出现」时，用命中的章节作答，并在句子里写明**这不是 frontmatter 的登记，是关键词命中**。宁可给一个标注了依据的近似答案，也不要一个空屏。

### 2.3 检索结果里存档章/卡照旧出现，但带标记

存档（`archived: true`）在 P2 的含义是「退出默认列表、退出任务材料」，不是「删掉」。检索是**查找事实**的通道，所以它照旧返回存档的章与卡（半透明、标「已存档」）——顺手把「这一章我撤了但还在被检索到」变成可见的事实。这与任务装配的取舍不同，因为两者的目的不同。

### 2.4 跨页签跳转用 token，不用路径

检索命中一张设定卡时，面板切到「设定」页并把路径交给 `SettingsView`。如果 `SettingsView` 只依赖路径，那么（a）再点一次同一张卡不会重新加载，（b）库刷新或忙闲状态变化引起的重渲染都可能重新读盘，**把作者没保存的编辑冲掉**。所以传的是 `{ path, token }`，视图只认 token 的变化。这是 P2「未保存缓冲」那条欠账留下的教训的直接应用。

### 3.1 检索引擎的断言（`spike/format-check.mjs` 新增）

纯函数，语料是手写的一小丛文档，所以那些「磁盘上很难摆出来」的情况可以直接写在断言里：

- 疑问词剥离与词条切分（含「在哪一章」「解释过」整段剥掉不留残字、只剩「了」的碎片不算词）；
- 「上次出场」按 frontmatter 登记作答、并给出全书出现章数；「第一次出场」与卡片 `firstAppear` 一致时说明一致；**不一致时报出矛盾**；
- 别名展开成同一实体（`默哥` → `chen-mo`），并且别名查询也会去正文里找；
- 关键词命中正文并带片段、**片段里的高亮坐标是片段自己的坐标系**（这是最容易写错的一处：先折叠空白再算坐标就会整体偏移）；
- 正文里没有的说法不会因为 n-gram 而误命中（「月光」）；
- 章纲也算命中理由；伏笔卡按生命周期作答并指出「尚未回收」；
- 设定文档（`settings/world.md`）在语料里；空查询不报错；命中统计与扫描数如实报告；
- 已存档的章仍可检索到，但带 `archived` 标记。

host 侧（内存 `ctx.fs` 替身）另加 5 条：一次扫描覆盖章节/卡/文档、命中正文并给出片段、读到 `settings/world.md`、答案指向真实章节、存档标记。

### 3.2 用真实输出眼检，抓到了断言抓不到的两个问题

检查全绿之后我把引擎的输出原样打出来读了一遍（临时脚本，已删），抓到两个**断言没覆盖、但读起来就是错的**问题：

1. 「陈默第一次出场**是哪章**」里 `是哪章` 没被剥掉，成了检索词；「解释过」剥完剩一个 `过`，于是**每一章都算命中**（`过` 字到处都是），把真正的答案压到列表后面。修法是补整段疑问短语（`在哪一章`/`是哪章`/`解释过`/`说明过`…）+ 「只剩一个虚词的碎片不算词条」，并补了 3 条断言钉住。
2. 「青铜镜第一次出现是哪章」完全没有答案（青铜镜还没有卡，见 §2.2）。

教训与 P2 那条一样：**断言能证明你想到的事，读一遍输出才能发现你没想到的事**。

### 3.4 落地当天在 GUI 里撞到的一次 404（不是代码问题，已查清）

M5 代码写完、构建完成之后，作者在面板里点「检索」拿到：

```
检索失败：host 返回了非 JSON 响应（HTTP 404）
```

**判定过程（先怀疑自己，再怀疑进程）**：`/api/novel/search` 在当天的构建里确实注册了（`ping` 的 `routes` 里有它，隔离实例上实测 200）；浏览器半也确实是新构建（新页签「检索」在，而它只存在于新 client bundle 里）。于是唯一剩下的解释是**运行中的 host 半还是旧构建**——证据是监听 3080 的进程起于 19:36:53，而最后一次构建是 19:28:11。

**结论**：`patchReload: live` 只热重载 `cordis.patch.yml`，**不替换插件模块**（源码证据与通用判定方法写进了 `01` §4）。所以这不是 M5 的缺陷，是「重建后 host 半要换进程」这个开发循环事实的一次现身。

**留下的改动**：`src/client/api.ts` 现在不再只说「非 JSON 响应」——遇到非 JSON 的 404 时它会去问一次 `/api/novel/ping`，把**运行中的 host 自己报告的路由表**写进错误里，并说明 host 半随进程加载。这样下一个人看到的是「运行中的 host 半报告了 N 条路由，里面没有它」，而不是一个要猜的 HTTP 状态。
