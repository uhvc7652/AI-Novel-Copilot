## 1. 目录树

```
<小说工程根>/
├── novel.yaml                        工程元数据
├── chapters/
│   └── v01/
│       └── c0001.md                  正文，一章一文件
├── settings/
│   ├── world.md                      世界观总纲
│   ├── timeline.md                   时间线（单文件，天然是一条序列）
│   ├── characters/<id>.md            角色卡
│   ├── locations/<id>.md             地点卡
│   ├── items/<id>.md                 物品/功法/道具卡
│   ├── factions/<id>.md              势力卡
│   ├── lore/<id>.md                  **通用设定卡**：境界阶梯、体系、术语、规则（哪个流派都能一张）
│   └── threads/<id>.md               伏笔/线索，一物一文件
├── outline/
│   ├── book.md                       全书主线、核心卖点、卷结构
│   └── volumes/v01.md                卷纲：卷目标、卷冲突、卷末状态（可选 frontmatter `title` = 卷名）
├── style/
│   ├── style-guide.md                文风规则
│   └── samples/*.md                  风格样本（你自己满意的段落）
├── .novel/                           机器数据
│   ├── history/<文档路径>/<时间戳>.json  行级修改历史（进 git，见 §4.9）
│   ├── checks.json                   一致性检查的忽略项（作者的决定，进 git，见 §4.7）
│   └── runs/<时间戳>-<任务>.json      AI 任务留痕（进 git）
└── exports/                          导出产物（派生，不进 git）
```

> **`.novel/` 里没有索引文件。** 早期版本在这里写过 `index.json` 与 `cache/`；P5 把它取消了——索引活在宿主进程的内存里，不是一个文件。原因见 §5。

**空目录不预先创建。** `settings/characters/` 这类目录在写下第一张卡时自然出现；脚手架只写有实际内容的文件。面板的卡片列表按类型分组显示，与目录是否存在无关。

## 2. 六项已定分叉

| # | 议题 | 决定 | 原因 |
|---|---|---|---|
| S1 | 章纲位置 | **写进章节 frontmatter 的 `beats` 字段**；卷纲只写卷目标 | 一章的"要发生什么"与"实际写成什么"同处一个文件，不会出现两处真相 |
| S2 | 设定卡组织 | **按类型分目录** `settings/<type>/<id>.md` | 文件管理器里类型一眼可见；索引按目录判类型 |
| S3 | 伏笔与时间线 | **伏笔一物一文件**；**时间线单文件** | 伏笔有生命周期（埋下/强化/回收/废弃），单文件才好追踪与 diff；时间线天生是一条序列 |
| S4 | id 风格 | **英文/拼音 slug**（`chen-mo`、`qingshi-town`） | 路径安全、跨平台无编码问题；中文名只做显示（`name` 字段） |
| S5 | 卷层 | **始终保留** `chapters/v01/`，单卷书也用 `v01`；**一卷「存在」= 它的卷纲文件存在，或它有章节**（2026-09-16 补，见 §4.11） | 结构统一；将来加卷不必搬家、不必改引用。后半句让「先计划一卷、再写它」成立：卷纲一落盘，这一卷就出现在大纲页、章节树与导出的卷列表里，哪怕一个字都还没写 |
| S6 | `.novel/` 与 git | 索引**不落盘**（在宿主进程内存里，见 §5）；`runs/`、`history/`、`checks.json` **进** git | 索引可重建、随进程消失，本来就没有"进不进 git"的问题；AI 任务记录、行级修改史，以及「这条检查我认了」都是作者的决定，不该丢 |

## 3. 身份、编号与引用规则

### 3.1 身份

- **章节 id 来自文件名**：`chapters/v01/c0001.md` → id `c0001`，卷 `1`，章号 `1`。
- **id 一旦写下永不改变**：在中间插入新章时，新章拿一个未使用的 id，**不重编号任何人**。章号顺序由 `number` 字段决定，与文件名无关。
- **章号全书连续，不按卷重数**（2026-09-16 明确）：第三卷的第一章接着前两卷往下排（第一卷写到第 100 章，第二卷就从第 101 章开始）。id 由章号推出（`c0101`），所以这条是 **id 全局唯一** 的前提——按卷从 1 重数会在第二卷里再造一个 `c0001`，而伏笔的 `plantedIn`、时间线的一格、章节的 `contextChapters` 都只写 id，撞了就没有第二种办法知道它们指的是哪一章。检查里的 `chapter-number`（重号）与 `chapter-gap`（缺号）因此也按**全书**判，不按卷判（`07` §1.1）。
- 设定卡 id 来自文件名：`settings/characters/chen-mo.md` → id `chen-mo`。

### 3.2 引用是单向的

引用一律用 id 字符串；索引负责反向查询（"这个角色出现在哪些章"）。

| 谁 | 引用什么 |
|---|---|
| 章节 | `pov`、`characters`、`locations`、`refs` → 卡片 id |
| 章节 | `contextChapters` → **章节 id**（参考章节：写作任务会读它们的**全文**，见 §4.2） |
| 伏笔卡 | `plantedIn`、`reinforcedIn`、`payoffIn` → 章节 id；`plantedQuote`、`payoffQuote` → 那一句原文 |
| 设定卡 | `relations[].to` → 卡片 id |

> **两套 id 空间不许混**：卡片 id 与章节 id 是分开的（`chen-mo` vs `c0001`）。`contextChapters` 里写的是章节 id，所以它**不进卡片的反向索引**（`project.ts` 的 `referenceIndex`）——混进去会让一张与某个章节 id 同名的卡凭空多出一次「出场」。

> **单一真相（已确认 2026-09-11）**：伏笔的生命周期**只由伏笔卡记录**，章节 frontmatter **不列** `foreshadowPlanted`/`foreshadowPaid`。理由是单一真相：同一个事实存两处，就会出现不一致而无法判断谁对。M6 查"埋了没回收"只需卡片一侧（`status` + `plannedPayoff` 对照章节进度）。若写章节时需要"本章埋了哪些线"，由索引提供**只读派生视图**，不落存储字段。

### 3.3 命名

- slug 规则：小写、`a-z0-9`、词间连字符；中文名转拼音或英文意译都行，只要**全局唯一**。
- 别名（`aliases`）只在卡片里登记，用于正文检索与冲突检测，**不参与路径**。填了别名，「青铜镜回收了吗」这类说法才问得出来（`12` §2.2）。

### 4.2 章节 `chapters/v01/c0001.md`

```markdown
---
id: c0001
volume: 1
number: 1
title: 楔子·雨夜
status: draft            # draft | revised | final
pov: chen-mo             # 视角人物，引用角色 id
targetWords: 3000
wordCount: 3120          # 由工具维护，不手写
beats:                   # 章纲：本章要发生什么（S1）
  - 陈默在雨夜捡到半块青铜镜
  - 被巡夜人撞见，仓皇逃走
summary: "陈默在雨夜捡到半块青铜镜。"   # 任务生成，可手改；这是检索的第一层索引
characters: [chen-mo, lao-zhou]
locations: [qingshi-town]
refs: [jian-xiu-jingjie]   # 本章依据的通用设定卡 id（境界阶梯、体系规则…），随章进 prompt
contextChapters: [c0007]  # 参考章节 id（可选）：这几章的全文会随写作任务进 prompt
tags: []
---

（正文从这里开始，编辑器只编辑这一段）
```

**这三行引用就是写作任务的材料**（2026-09-12 明确）：`characters` / `locations` / `refs` 里的卡，都会以 `## <id>` + 卡片字段 + 正文的形式进「按章纲写整章」「续写」「改写」「扩写」「润色」的 prompt（`client/tasks.ts` 的 `assembleCommon`）。**没有上限**（2026-09-15 取消）：作者主动挂在某一章上的卡**全部**进 prompt，一张不落——曾经有个「最多 6 张」的截断，而那和「面板显示了一张卡而 prompt 里没有」是同一类谎。**「去 AI 味检查」不带卡**——它是检查器，卡只添噪声；它的输入清单里也不会假装读过。

**面板的正文页有一行「本章引用的卡」**（同日；`client/ChapterCards.tsx`，单独一个组件，所以它能被渲染检查直接喂夹具）：点「＋ 加卡」从设定库里挑一张，点 chip 上的 × 移除。它**按卡的类型**决定写进哪个字段——角色 → `characters`、地点 → `locations`、物品/势力/设定/伏笔 → `refs`（规则是 `novel/cards.ts` 的 `chapterRefFieldOf`），所以面板这一行与大纲页那三个按 id 填的框是同一份数据的两个视图。**为什么不一律写进 `refs`**：`characters` 与 `locations` 被 `pov-unlisted` 与检索的「谁出现在哪些章」按字面意思使用，把它们当杂物箱会让那两处回答撒谎。

**这一行不许「看起来少了一张卡」**（2026-09-14 重做，作者两次报「新建的方衡在加卡里没有看到」）：①**下拉列出设定库里每一张活卡**，已经引用的那张标「已引用」并置灰——此前是**直接隐藏**，而那正好会被读成「我的新卡没出现」；已存档的卡仍然不列。②旁边写着**库里有多少张活卡**与**本章引用了几张**（「生成时会全部带上」），再旁边是**「刷新」**；进正文页/切章时自动重读一次设定库。③**读失败不再被吞掉**：打开工程时那次读卡失败原本是 `.then(setLibrary, () => {})`，于是界面可能拿着几小时前的旧列表而毫无提示——现在失败会写明原因，「刷新」可重试。这三条合起来的意思很直接：**列表为空只可能是「库里真的没有」**，而库里有几张是会显示出来的。

**「有没有未保存的改动」比的是整份 frontmatter**（2026-09-14 修，`novel/buffer.ts` 的 `documentChanged()`）：此前正文页只比 `body` / `title` / `status` / `targetWords`，而 `characters` / `locations` / `refs` / `beats` / `archived` 同样可编辑——于是**在正文页加一张引用卡之后，「保存」按钮是灰的、切章与关页面都不问、那张卡在切章后就没了**（作者书里的 `境界-凌空` 就是这么丢的）。三个持有文档的编辑器（正文 / 设定 / 大纲）现在都走这一个函数，`client-load-check` 还有一条源码规则守着「不许自己列字段」。**它单独一个模块而不是放在 `document.ts` 里**：那个模块 import 了 YAML 解析器，客户端一旦 import 它，浏览器 bundle 里就会多出一条外壳**模块表答不上来的 require**，插件会**在加载时直接抛**（那一次真的把面板弄崩了，见 README 教训 8）。

**上一章与参考章节是写作任务的故事材料**（2026-09-16 明确，作者要求「续写、扩写时至少要把上一章加入 prompt」，粒度选定为「上一章全文 + 摘要」并允许自己再挂几章）：`client/tasks.ts` 的 `storyChapters()` 给**五个正文任务**（整章 / 续写 / 改写 / 扩写 / 润色）各带两节——

- `【上一章】第 N 章 <标题>` + `摘要：…`（frontmatter 的 `summary`，有才写）+ `全文：…`。取的是**活着**的上一章（存档章不是故事材料，这条老规矩不变），章号严格小于本章的最后一章。
- `【参考章节】第 N 章 <标题>` + `摘要：…` + `全文：…`，一章一节，按 `contextChapters` 里写下的顺序，**没有上限**，页面与输入清单里都数得出来。

三条边界写在明处：**模型检查仍然只要上一章的摘要 + 结尾 800 字**（`08` §2.2 明写「不喂其它章节正文」，它判的是这一章）；**「去 AI 味检查」不带任何章节正文**（它关于文风，输入清单不许说了没读）；**重复的章不会进两次**——本章自己、以及已经作为【上一章】进 prompt 的那一章，都会在装配时被跳过（与卡片引用同一个道理：作者手写的 id 不该变成重复的 token）。

**面板的正文页有一行「参考章节」**（同日；`client/ChapterContext.tsx`，与「本章引用的卡」并排、同样单独一个组件）：点「＋ 加章节…」按卷分组挑一章，点 chip 上的 × 移除；已引用的标「已引用」，**本章自己与已存档的章都不出现在可选列表里**。提示语明说「上一章已经自动带上」——不说的话，作者会以为上一章没进 prompt，再手挂一次。chip 对三种查得到但用不上的 id 各说一句为什么（已存档 / 就是本章 / 工程里没有这一章），因为它们正是 `context-ref` 要报的东西。大纲页的章纲编辑器也多一个按 id 填的**参考章节**框，与正文页是同一份数据的两个视图。

### 4.3 角色卡 `settings/characters/chen-mo.md`

```markdown
---
id: chen-mo
type: character
name: 陈默
aliases: [默哥, 陈小子]
role: 主角
age: 19
gender: 男
tags: [剑修, 世家弃子]
firstAppear: c0001
relations:
  - { to: lao-zhou, kind: 师徒 }
  - { to: su-ling, kind: 青梅竹马, secret: true }
---

## 外貌
## 性格
## 能力/境界（含成长曲线）
## 动机与弧光
## 不可违背的设定（硬约束）
```

地点/物品/势力卡同构，`type` 分别为 `location`/`item`/`faction`，正文分节按各自需要（如地点用"地理/氛围/势力归属"，势力用"立场/实力/关键人物"）。

**「同构」只是骨架相同**（2026-09-12 补充）：`id` / `type` / `name`（伏笔卡是 `title`）/ `aliases` / `tags` / `archived` 是每张卡都有的，**可选字段则按类型给**——`role` 属于角色卡（身份）与势力卡（立场），`age` / `gender` **只属于角色卡**，生命周期那几个字段只属于伏笔卡（§4.4）。这张表只有一份：`src/novel/cards.ts` 的 `CARD_FIELDS`（判定是 `cardHasField()`）——面板的表单按它决定显示哪些框，`cardFacts()` 按它决定往 prompt 里发哪些字段。所以手写进地点卡的 `age: 三百年` 会原样留在文件与摘要里，但不会被当成「年龄」发给模型；面板也不再给地点卡和物品卡摆出角色的年龄、性别框（那是作者报的第三条：**地点、物品的编辑界面和角色卡一模一样**）。

**正文分节与占位提示是同一份表**（2026-09-12 收拢）：`novel/cards.ts` 的 `CARD_SECTIONS` 说每种卡的正文分节——角色「外貌/性格/能力·境界/动机与弧光/硬约束」、地点「地理/氛围/势力归属/硬约束」、物品「来历/能力·用途/硬约束」、势力「立场/实力/关键人物/硬约束」、通用设定「定义/分级/条件与代价/边界」、伏笔「埋点方式/读者应有的疑问/回收设计」。新卡的脚手架（`io.ts` 的 `cardSections`）与面板卡片框里的占位提示（`cardBodyHint`）**读同一张表**，所以提示不会描述一个脚手架并不写出来的形状；**分节不是校验**，写成别的照样合法。

**通用设定卡 `settings/lore/<id>.md`（`type: lore`，2026-09-12 加入）**：世界设定里既不是人、也不是地点/物品/势力的那一类——境界阶梯、力量体系、术语、组织制度、规则。**一个流派一张卡**，正文分节是「定义 / 分级 / 条件与代价 / 边界（不可违背的部分）」，阶梯写在「分级」里。它的由来是一个很具体的问题（作者问的：「不同流派的境界设定放哪里，全放世界观太臃肿」）：`settings/world.md` 是**总纲**，而且**只有「一致性检查（模型）」会整份读它**（`client/tasks.ts` 的 `include(ctx, WORLD_FILE, …)`），细则堆在那里既让每次检查变胖，又不是写作时真正被读到的东西。

**章节用 `refs` 直接引用它们**（同日）：`refs: [jian-xiu-jingjie]` 与 `characters` / `locations` 并列，id 空间相同（§3.2）。被引用的卡与出场角色卡走同一条路进**生成** prompt（「按章纲写整章」），所以「开章时引用一下流派设定」直接生效；`refs` 里的错 id 会被 `missing-ref` 抓住，检索也把它算作「这张卡被哪一章用过」。**为什么单开一个字段而不是塞进 `characters`**：那个字段被 `pov-unlisted` 与检索的「谁出现在哪些章」按字面意思使用，把境界体系写进去会让这两处撒谎。`locations` 仍然不进生成 prompt（写正文历来不读它）——一章真要依据某个地点，把它写进 `refs` 是明确的那条路。

**`age` 与 `gender`**（`gender` 于 2026-09-12 加入）：都是可选、自由文本的**展示事实**——`age: 19` 是约定而不是规则，写成「十九」同样合法，面板的输入框也不会把非数字写成 `NaN`。它们**只属于角色卡**（`CARD_FIELDS`），**不参与**索引、排序或校验，但**会随角色卡进 prompt**：`client/tasks.ts` 的 `cardFacts()` 把「名字/别名/身份/年龄/性别/标签」合成一行放在卡片块的开头，因为「主角几岁、是男是女」正是生成时最容易写错的东西。没填的字段一个字都不会发出去（空模板不进 prompt 的规矩不变）；这张卡的类型没有的字段同样不发，哪怕文件里手写着（按 `cardHasField()` 过滤）。

**`role` 可以是多个**（2026-09-12 明确）：一个角色常常同时是「主角」和「前朝皇子」，所以这个字段和 `aliases` / `tags` 一样**容忍纯标量与列表两种写法**：

```yaml
role: 主角
role: [主角, 前朝皇子]
```

面板写回时**一个写成标量、多个才写成列表**：老文件因此一个字节都不会变，git 里也没有无谓的改动。摘要与 prompt 里多个身份用 `、` 连成一行（`身份: 主角、前朝皇子`）。

**面板上的列表字段一律走 `client/ListField.tsx`**（2026-09-12 修）：逗号在输入过程中会被保留，离开输入框（blur 或回车）才解析成列表。此前那些框的 `value` 就是**解析后的列表**，于是打一个逗号就被回写抹掉——「标签里无法输入逗号」是这个 bug，别名与大纲页的出场角色/地点也一样，所以修成同一个组件。

### 4.4 伏笔卡 `settings/threads/th-003.md`

```markdown
---
id: th-003
```

**伏笔的生命周期只由这张卡记录**（§3.2 的单一真相）：章节 frontmatter **不列**「本章埋了哪些线」。

**`plantedQuote` / `payoffQuote`**（2026-09-12 加入）：存的是**那一句本身**，不是字符偏移。理由是偏移会被它上面任何一个编辑废掉，而一句话不会；而且那句话被改写时，定位会**明说找不到**，不会安静地指向「现在占那几个字符的随便什么东西」。它们由面板在正文里记录/回收时写入（`12` §1.4），可以手改，**不会自动跟着正文更新**——正文改了原句之后，列表里显示的仍是当初记下的那句话。**M6 为此有一条规则 `thread-quote`**（同日补，见 `07` §1.1）：原句在它记录的那一章里找不到了就报一条警告；用的是面板同一个 `findQuote`（`src/novel/quote.ts`），所以「检查说没意见」与「点跳回埋点能选中」不会互相矛盾。它只报不改：哪一句才是这条线，只有作者知道。

**id 由面板生成**为 `th-NNN`（`12` §1.5）。手写的 slug 同样合法（`03` §3.3 的 slug 规则），只是不参与自动编号。这里用 `th-` 而不是 `fs-`：地点卡的示例 id 也是 `fs-NNN`，两棵树共用前缀会让读者分不清。

**「删除」这张卡**同样是 `archived: true`（§4.6），生命周期另有自己的 `status`，两者不共用字段。**但两者都能让一条线「退场」**（2026-09-12 明确）：`status: abandoned` 表示这条线被放弃了——卡留着（「伏笔」页签的已废弃组要能看见自己丢掉了什么），可是**它的名字重新可用**，检索不再把它当实体来答，任务装配也不再把它当可用设定。判断只有一份：`src/novel/cards.ts` 的 `isRetiredCard()`（面板与 host 共用）。把状态改回去，这一切都回来。

### 4.5 时间线 `settings/timeline.md`

单文件，按叙事顺序排列，每条引用章节 id：

```markdown
# 时间线

| 叙事序 | 故事时间 | 事件 | 章节 |
|---|---|---|---|
| 1 | 元启三年·春 | 陈默被逐出家族 | c0001 |
```

**这张表是「检查」和面板共用的一个东西**（2026-09-12 补）：`src/novel/timeline.ts` 的 `parseTimeline` / `renderTimeline` 是唯一的解析与渲染——M6 的 `timeline-ref`（引用不存在的章）与 `timeline-order`（某行的章比上一行更早）读它，面板的「时间线」页签用它做逐行编辑（故事时间 / 事件 / 章节 id，章节可从已有章节里选）。**叙事序由面板按行号重排**：它表示叙事顺序，而改顺序的动作就是编辑器里的 ↑↓，检查从不读这一列（它比的是章节）；手写了一个与位置不符的号，保存时会被归一。

**一格可以写多章**（`c0001、c0002`）：检查会把这一格里的每个章节 id 都算进去。**表之外的内容原样保留**——`# 时间线` 标题、表下面的笔记都不会被编辑器碰掉；文件里还没有表时，改一行就会追加一张（并且检查在那之前不对时间线发表意见）。单元格里的 `|` 会被换成全角 `｜`，否则会把表格拆坏。

### 4.6 存档（面板里的"删除"）

面板的删除动作写 `archived: true`；勾"显示已存档"可以找回并清除该字段。

```yaml
archived: true           # 可选；不写表示在用
```

**适用范围**：设定卡与章节都可用这个字段。

| | 存档后 |
|---|---|
| 设定卡 | 退出默认列表；不参与「可用设定 id」的装配；**不参与一致性检查里命名与生命周期类的规则**（名字/别名撞车、伏笔的引用与状态与原句、卡片关系、`firstAppear`） |
| 章节 | 退出章节树与大纲页的章节列表；**退出**书稿的章数与字数统计；**退出**任务的故事材料——不会被当成「上一章」锚定续写，也不会被「拆章」当成已排的章，**也不管作者有没有把它手挂成参考章节**（装配跳过它，`context-ref` 会提示一句「已存档，生成时会跳过」）；**退出**一致性检查里「关于它自己」的规则（字数偏离、视角人物没登记、它自己的引用指向不存在的卡，以及 `firstAppear` 的「最早出场」比较）——但 **id 与章号照旧参与**（见下） |

**存档 ≠ 从世界上抹掉**（2026-09-12 补，起因是作者点出「删掉的伏笔还在检查里」）：存档的 **id 仍然有效**——解析引用时照样算上它，所以删一张卡不会让引用它的每一章突然变成「引用不存在的卡」（那种情况由 `archived-ref` 提示说出来）；同理，**存档章的 id 与章号也不释放**，所以 `id-mismatch`（声明的 id 与文件名不一致）与 `chapter-number` / `chapter-gap`（重号、缺号）**照旧把存档章算进去**。划下的这条线是：**「关于它自己」的规则只对作者还在用的一组说话，而「作为引用目标 / 占号者」对所有文件说话**。恢复那个文件，前面那些规则全部回来。

三个约束：

- **不用 `status` 表达存档**：伏笔卡的 `status` 是生命周期（`planted`/`reinforced`/`paid`/`abandoned`），章节的 `status` 是成稿状态（`draft`/`revised`/`final`），一个字段两种含义就会互相覆盖。
- **章节的 id 与章号不释放**：存档的章仍占着 `c0002` / `number: 2`，下一章照旧往后排。这样恢复它不会与任何人的引用撞车，也不需要重编号任何人（§3.1 的身份规则从这里往后才成立）。
- **这是格式层面的降级，不是实现偷懒**：`ctx.fs` 的能力面只有 resolve / stat / lstat / list / read / write / edit——**没有任何删除原语**，DSH 给 agent 的文件工具也一样（`packages/fs/fs/src/index.ts`）。而 P0 定的规矩是「`ctx.fs` + 沙箱策略是唯一的门」，绕过它去 `node:fs` 等于把作者的文件策略作废。硬删除只能由作者在文件管理器里做，或等 DSH 提供删除原语。

### 4.7 一致性检查的忽略项 `.novel/checks.json`

面板上「忽略」某条检查结论时，记住的是它的 **issue key**，形如 `规则:文件:目标`：

```json
{
  "ignored": ["missing-ref:chapters/v01/c0001.md:qingshi-town"]
}
```

- **key 描述事实，不描述那句话**：改一句提示文案不该让作者做过的判断复活（M6，`src/novel/checks.ts`）。
- **为什么不在 `.novel/index.json`**（需求 §4 M6 原本这么写）：那时把索引定义成「可重建、不进 git 的缓存」，而「这条我认了」是**作者的决定**。存进派生缓存意味着它会在某次重建后无声消失，也永远不会被提交。理由与 §4.6 的存档同源：作者说过的话要留在能被 git 记住的地方。（P5 之后这个索引文件整个取消了，见 §5；这条理由反而更强：一个连文件都没有的缓存更不该存作者的决定。）
- **对不上的 key 不是错误**：问题被修好之后，对应 key 就对不上任何 issue，此时只提示「N 条忽略记录已经对不上任何问题」，不报错、不阻塞检查。

### 4.8 文风 `style/style-guide.md` 与样本
`style-guide.md` 是规则清单（人称与叙述距离、句长与节奏、禁用词与 AI 味清单）；`samples/*.md` 是作者认可的段落，作为生成时的风格锚点。两者都是纯 Markdown，无 frontmatter 要求。

### 4.9 行级修改历史 `.novel/history/<文档路径>/<时间戳>.json`

**面板每写一次可编辑文档，就落一版**（M7）。一份文件 = 一版的完整状态：

```json
{
  "at": "2026-09-12T10:20:30.123Z",
  "path": "chapters/v01/c0001.md",
  "action": "update",
  "source": { "kind": "task", "label": "润色本章" },
  "before": "---\nid: c0001\n…整份旧文件…",
  "after": "---\nid: c0001\n…整份新文件…"
}
```

- **目录按文档路径分家，不按 id**（`history/chapters/v01/c0001/…`）。需求原文写的是 `<章节 id>`；改掉的理由是结构性的：M7 覆盖的不是只有章节（卡、卷纲、单文件页同样有撤销），而章 id 与卡 id 都是朴素 slug，按 id 分家时一张叫 `c0001` 的卡会和第 1 章共用一份历史。
- **`action` 由两版内容判定**：没有 `before` 是 `create`，翻转 `archived` 是 `archive`/`restore`（存档是本格式的删除，见 §4.6），由回滚产生的是 `revert`。作者要看的「删除了」就是那个 `archive`。
- **`source` 记录这次修改从哪来**：`manual`（面板里手写保存）、`task`（采纳某次生成后保存）、`revert`（回滚）。只有面板知道这件事，所以它随写入请求一起发过来。
- **回滚写的是某一版的 `after`，不是 `before`**。新建那一版没有 `before`，写回去会得到一份没有 frontmatter 的空文件。`after` 在任何情况下都是一份合法文档，所以建章那一版也能安全回滚。回滚本身也是一次写入，因此会被记成一版——回滚可以再回滚。
- **时间戳在记录内唯一**（被占用就顺延一毫秒）。它同时是文件名和「取哪一版」的标识，两份记录共用一个时间戳就等于有一版够不着。
- **一字未改的保存不产生版本**；`novel.yaml`、`.novel/*`、`runs/` 也不是文档，不进这里。
- 与 git 的边界：git 是**文件级**历史（每章一次落盘），这里是**行级**的。面板外的改动不会被记录。

### 4.10 导出产物 `exports/<书名>-<范围>-<时间戳>.md|txt`

P5 的导出把整本书渲染成**一个文件**（`00-requirements.md` §2.2：v1 只做 md / txt），落在 `exports/`：

```markdown
# 书名

中文长篇网文 · 共 3 章 · 约 125000 字

## 第 1 卷

### 第 1 章 御剑

（正文）

### 第 2 章 巡夜人
```

- **只导没存档的章**（§4.6）：存档是把一章撤出故事，它就不该出现在交出去的稿子里。
- **frontmatter 不出门**：`id` / `wordCount` / `beats` 是机器事实，导出是给人读的。
- **txt 与 md 只差脚手架**：正文逐字相同，`txt` 只是没有 `#`。**不改写正文**——换行重排、全角化、加缩进都是排版，做了就等于多出第二个版本的稿子。
- **名字里带时间戳**，所以两次导出是两个文件，不会覆盖彼此（`exports/` 不是版本库）。书名里的 `\ / : * ? " < > |` 换成横杠而不是删掉：`第1章:雨夜/前传` 少一个冒号就是另一个标题。
- **章标题自带章号时归一**：`第二章 巡夜人` 在第 2 章导出为 `第 2 章 巡夜人`，而不是 `第 2 章 第二章 巡夜人`。只有前缀数值**等于**该章章号时才摘（中文数字也认）；对不上就原样保留——`第三章` 出现在第 5 章是书里的事实，删掉它等于把矛盾藏起来。
- **不是文档**：`exports/` 不在 §3 之外的可编辑白名单里（`paths.ts` 的 `isDocumentPath`），因此它没有编辑面、不进修改记录（§4.9）、面板只在导出页签里列出来。
- **卷标题用卷名**（2026-09-16 补，§4.11）：作者给卷起了名字时，卷标题是 `## 第 2 卷 · 北境篇`，没起名就只有 `## 第 2 卷`。卷号永远在最前面——它是唯一不可能缺席的那一半。

### 4.11 卷与卷纲 `outline/volumes/v01.md`

**一卷「存在」= 它的卷纲文件存在，或它有章节**（S5）。卷纲因此不只是「这一卷的说明」，它还是**一卷被计划过的证据**：

```markdown
---
title: 北境篇          # 可选：卷名。不写就是「第 1 卷」
---

# 第 1 卷

## 卷目标
## 卷冲突
## 卷末状态
```

- **卷号来自文件名**：`outline/volumes/v02.md` → 第 2 卷（`volumeOutlinePath(2)`，与 `chapters/v02/` 同一个号）。
- **卷名是可选 frontmatter `title`**：`VolumeSummary.title`；下拉（大纲页 / 导出页 / 参考章节）、章节树的卷标题与导出的卷标题都用它。**不预先写进骨架**——「没有名字」与「名字是第 2 卷」是两件不同的事，而后者会让导出印出「第 2 卷 · 第 2 卷」。
- **卷纲正文是散文**：散文三节（卷目标 / 卷冲突 / 卷末状态）由作者写，也可以由「续写卷纲」生成。骨架只有一份（`paths.ts` 的 `volumeOutlineSkeleton`），新工程的脚手架与面板的「新建卷」写的是同一个文件。
- **新建一卷不预先造目录、不预先造章**：只写这一份卷纲（§1「空目录不预先创建」）。这一卷立刻出现在所有卷下拉与章节树里，章节由「＋ 新建章节」或「按卷纲拆章」产生——**章号接着全书往下排**（§3.1），所以第二卷的第一章是第 N+1 章、id 是 `c000N+1`。
- **删除一卷没有原语**：`ctx.fs` 没有删除（§4.6），所以这一轮只做「新建 + 命名 + 切换」。真要删掉一卷的卷纲文件，只有 `tools/` 下那些在作者终端里跑的脚本能做到。

## 5. 派生数据（永不手写）

| 数据 | 位置 | 来源 |
|---|---|---|
| 章节字数 | 前端实时算 + 保存时写入 `wordCount` | `countWords`：中文字符数 + 英文/数字词数 |
| 章节、卡片与单文件页的**解析结果** | **不落盘**：宿主进程内存里的扫描缓存（P5，`src/novel/cache.ts`） | 扫描章节与卡片；每个文件按 `ctx.fs` 的新鲜度令牌（`dev:ino:size:mtimeNs:ctimeNs`）判断可否复用，令牌变了就重读重解析 |
| 反向链接（角色出现在哪些章） | 由上面的扫描现算，不缓存（P2 起由面板请求时派生，见 §3.2） | 章节 frontmatter 的引用 + 卡片 id（`contextChapters` **不参与**：它引用的是章节，不是卡片——见 §3.2） |
| 检索结果（实体、命中片段、答案） | **不落盘**，每次请求当场派生（M5，`src/novel/search.ts`） | 章节 frontmatter 与正文、卡片字段与别名、各单文件页 |
| 一致性检查报告 | **不落盘**，请求时派生；作者点「保存报告」才写入 `.novel/runs/<时间戳>-consistency.json`（M6） | 确定性规则（`src/novel/checks.ts`）扫章节、卡片与各单文件页 |
| AI 任务记录 | `.novel/runs/*.json` | 每次任务执行：输入清单、提示词、原始输出 |
| 行级修改历史 | `.novel/history/<文档路径>/<时间戳>.json`（**进 git**，见 §4.9） | 面板每次写入一版：`before`/`after` 全文、动作、任务来源；diff 不落盘，取一版时当场算 |

**索引永远可重建**，所以它不允许成为唯一真相；**它也不落盘**，因为它没有理由需要活过一次宿主进程：

1. 百万字的冷扫描是半秒级（1000 章 / 311 万字实测 0.58 s），一个插件实例的生命周期就是一次宿主进程——落盘换来的是「下次开进程省半秒」。
2. 几 MB 的 JSON 在每次保存章节时重写，成本高于它省下的读取。
3. 磁盘上的索引会留下「昨天的索引还在」这种可以撒谎的状态；进程内的副本随进程消失。

**缓存的是字节，不是判断。** 每次扫描照旧列目录、逐个比对令牌，所以「答案来自磁盘现在的内容」没有被缓存吃掉：在面板之外改一章，下一次请求就看得见。做错这件事的方式只有一种——把「依赖别的文件的派生值」也缓存起来（`appearsIn` 就是这种值，它每次都现算）。完整设计与实测数字见 `10-p5-performance.md`。

> **没有做倒排索引**，尽管这一行以前写的是它。实测把暖检索拆开（400 章 / 124.5 万字）：目录列举约 120 ms、重建语料约 2 ms、全文 n-gram 匹配约 12 ms——倒排索引能拿掉的只有最后那 12 ms，却要背上「位置与片段必须与 n-gram 语义逐字一致」的一致性风险。数字与取舍见 `10` §3.3。

## 6. 扩展规则

- **新增卡片类型**：在 `settings/` 下加一个目录 + 一种 `type` 值即可，不改动已有文件。章节 frontmatter 若要引用它，再约定一个字段名。
- **不引入数据库**：v1 全部是纯文本；索引只是宿主进程内存里的一个缓存（§5）。
- **不引入二级目录**：除 `settings/<type>/` 与 `chapters/vNN/` 外不再分层，避免路径推导变复杂。
