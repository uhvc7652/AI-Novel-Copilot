# M7 · 修改记录：面板内的行级历史与回滚

> 需求 §4 M7 是唯一一个从头到尾没开工过的模块。它写得很短：记录每次修改、可对比不同版本、支持回滚、面板可查看、点击跳转到正文位置、落盘 `.novel/history/<章节 id>/<时间戳>.json`（存 `before`/`after` 全文与任务来源）。
>
> 这一期把它做完了。下面记的是**需求没说、但必须决定**的那些事。

---

## 1. 与 git 的边界（需求已经划好，这里只是落实）

需求 §4 M7 的备注写得很清楚：**git 是文件级历史**（每章一次落盘），**M7 是面板内的行级历史**。这条边界决定了这个功能的形状：

- 面板要回答的不是「这一章什么时候改过」，而是「**那次「润色本章」到底把哪一句改成了什么**」。所以核心是一个行级 diff，而不是一串时间戳。
- diff 在 **host 侧**算（`src/novel/history.ts`），不是浏览器里算。理由与 M5/M6 一样：有意思的判断（什么算一次改动、整篇重写怎么呈现、折叠后作者还看得到哪几行）应该在一个不需要浏览器就能跑的模块里，能被检查脚本钉住。
- 「删除」在本格式里是**存档**（`03` §4.6，DSH 没有删除原语）。所以记录里的动作不是「修改」一种：翻转 `archived` 的那一版记成**存档**或**恢复**——需求要的「包括新增、删除、修改」，作者要看的正是那个「删除了」。

## 2. 四个需要记录的决定

### 2.1 回滚写的是 `after`，不是 `before`

「回滚到这一版」最直觉的实现是「把它记录的 `before` 写回去」。**这是错的**，而且错在一个致命的地方：**新建**那一版没有 `before`（文件当时不存在），写回去就是一个没有 frontmatter 的空文件——一份损坏的文档，而且无从恢复。

每一版的 `after` 在任何情况下都是一份完整、合法的文档，所以回滚写 `after`。`before` 只用来算 diff。这样建章那一版也能安全回滚（回到建章时的空正文），不需要为它开特例。

### 2.2 版本的身份是**时间戳**，因此时间戳必须唯一

需求把文件命名为 `<时间戳>.json`，`at` 自然就成了「取哪一版、回到哪一版」的标识。问题在于毫秒并不唯一：**同一毫秒内的两次保存会拿到同一个 `at`**，于是「回滚到 `at`」会命中目录里先被读到的那一个——**回滚到错误的版本**。

这不是推理出来的，是检查脚本先撞上的（§4.1）。修法不是给文件名加后缀绕过，而是**在执行写入时就保证时间戳唯一**（`freeHistoryStamp`：占用则顺延一毫秒）。代价是同一毫秒内的第二版会比时钟晚一毫秒，这是对一个派生值的取整，不是对作者正文的伪造。

顺带清掉了一个更隐蔽的坑：如果真用了 `-2` 后缀，`…-123Z-2.json` 在字典序上排在 `…-123Z.json` **前面**，而列表正是按文件名取「最新 N 条」——那会丢掉较新的那一版、留下较旧的。一个静默消失的版本，是这个记录最不能有的失败。`compareHistoryFiles` 把这条排序规则写在明处，即使唯一性已经让后缀不再出现。

### 2.3 崩溃与降级：写入失败不能反过来毁掉保存

两处「故意不失败」：

1. **一字未改的保存不产生版本。** 否则记录会被「没区别」的条目填满，作者就不再看它了。
2. **记录写失败不影响保存。** 走到那一步时章节已经在磁盘上了，报「失败」等于报错的东西。所以只记一条 warning 日志，保存照常成功。

第 2 条有个欠账：**面板不会告诉作者「这一版没记上」**（§5）。

### 2.4 `Ctrl+Z` 绑在「修改记录」页签里，不绑在编辑器上

需求写的是「支持回滚(Ctrl+Z)」。直接绑到正文 `textarea` 上是个**净损失**：作者一边打字一边按 Ctrl+Z，是想收回一句话，而浏览器原生的撤销今天正好在做这件事；同一个键改成「回滚整篇文档」，等于在「撤销」的名义下丢掉上一次保存以来的所有笔迹。

所以快捷键绑在**这个页签里**：这里编辑器不在屏幕上，Ctrl+Z 没有别的含义，按下去就是「回滚到上一版」（带一个念出时间的确认框）。编辑器保留它自己的撤销。

这是一处**对需求原文的偏差**，理由是「两条撤销不能抢同一个键」。真正的全局快捷键策略属于 P5 的「快捷键」那一块，到时候可以给文档级回滚一个不冲突的组合键。

### 2.5 目录按**文档路径**分家，不是按章节 id

需求写的是 `history/<章节 id>/`。实现改成 `history/<文档路径去掉 .md>/`（`history/chapters/v01/c0001/…`），两个理由都是结构性的：

1. M7 要记录的是**每一个可编辑文档**，不只是章节。卡、卷纲、`style/style-guide.md` 都走同一个面板保存通道，也都该有撤销。
2. 章 id 与卡 id 都是朴素 slug（`c0001`、`chen-mo`）。按 id 分家，作者只要把一张卡命名为 `c0001`，两者就会共用一份历史。检查脚本专门留了一条断言钉这件事。

## 3. 实现

### 3.1 host 半

| 文件 | 做了什么 |
|---|---|
| `src/novel/history.ts` | **纯模块**：`diffLines`（行级 diff）、`diffRows`（折叠出作者真正要看的那些行）、`actionOf`（新建/修改/存档/恢复/回滚）、`parseHistoryEntry`（宽容解析）。零依赖，浏览器也能 import |
| `src/novel/paths.ts` | `historyDirOf` / `historyStamp` / `historyFileOf` / `freeHistoryStamp` / `compareHistoryFiles`——路径与身份规则，与其它格式规则放在一起 |
| `src/novel/io.ts` | `write()` 成为**唯一的记录点**：章节、卡、大纲、单文件页、以及回滚自身都从这里过，所以没有任何一条写入路径能忘记记版本。新增 `history()`（列表，默认最近 50 条）、`historyEntry()`（单条 + 全文）、`revert()`（写回某一版的 `after`） |
| `src/novel/http.ts` | `/api/novel/history`：`GET` 列表、`GET ?at=` 单条带 diff、`POST action=revert`。另外 `/chapter` 与 `/doc` 的写入开始接受 `source` |

diff 用的是「先剥掉公共前缀与后缀，再对中间做 LCS」，超过 400 万格就退回「全部删除 + 全部新增」的粗粒度描述。这个上限**不是为了性能，是为了不撒谎**：精确对齐一篇巨大文档的代价是内存，而「整篇换掉了」本来就是那件事的诚实说法。一章的整篇重写（200 行左右）离上限很远，检查脚本钉住了这一点。

### 3.2 浏览器半

| 文件 | 做了什么 |
|---|---|
| `client/HistoryView.tsx` | 版本列表（时间 / 动作 / 来源 / 字节变化）→ 选中一版看 diff → 点任意一行在正文里定位 → 「回滚到这一版」「回滚到上一版」 |
| `client/Panel.tsx` | 第六个页签「修改记录」；记住「当前缓冲区里的正文是谁写的」（`provenance`），保存时随写入带上；回滚后把结果接回编辑器并刷新工程树 |
| `client/api.ts` | `readHistory` / `readHistoryEntry` / `revertHistory`；`writeChapter`、`writeDocument` 带上 `source` |

**任务来源是这样传的**：任务把正文放进编辑器缓冲区（M7 之前就已如此），作者再点保存。所以「来源」只在面板里知道，`Panel` 在采纳时记下任务标签，保存时随请求发出，**保存后清零**——下一版是作者自己的改动，除非又采纳了一次生成。

## 4. 怎么验的

### 4.1 检查脚本（`spike/format-check.mjs`，本节相关的新增，总计 213）

纯模块部分：同一文本零增删、新建不产生「删掉空行」、中间插入/删除/替换各只报对应的一增一删、行号归属（删的行报 `before`、增的行报 `after`）、末尾换行也算改动、超上限退回粗粒度且一行不丢；折叠：长段折成一行提示且改动点还在、**显示行数加折叠行数等于 diff 长度**（不丢行）、展开不折、短段不折；存储：目录按路径分家、时间戳文件名不含冒号、同毫秒排序、`freeHistoryStamp` 让位一毫秒、动作判定、条目解析的宽容与严格。

io 部分（内存 `ctx.fs` 替身）：写入即记录、最新在前、任务来源随写入落盘、**一字未改的保存不产生版本**、取一版带全文与 diff、回滚换回正文、**回滚本身也是一条版本**、回滚再回滚、存档被记成「存档」、limit 只读最近 N 条、非文档路径拒绝、不存在的版本 not-found、同名 id 的卡与章各有各的历史、历史只记四棵内容树（不记 `novel.yaml` / `.novel` 自己的文件）。

> **写这一节时被自己的断言抓出三个真问题**（都不是读代码发现的）：
> 1. **同一毫秒的两版 `at` 相同**，按 `at` 取版本会拿到错的那一版——检查脚本里「回滚到第一版」真的回滚到了第二版。这是 §2.2 那个修法的由来。
> 2. **回滚被记成了普通的「修改」**：`revert` 写的是某一版的 `after`，从内容看就是一次普通编辑，于是记录里最值得看的那一行被藏了起来。修法是把「谁写的」纳入动作判定（`actionOf` 收 `source`）。
> 3. 一条 M6 时期的旧断言（`.novel/` 下只有 `checks.json`）因为新增了 `history/` 而变红。它要钉的其实是「忽略项没有泄漏到别的机器文件、那个可重建的 `index.json` 根本不存在」，所以改成显式排除 `history/` 并补上对 `index.json` 的否定断言。

### 4.1b 作者点出来的第三个真 bug：修改记录只看得到章节

交付后作者试了一下：「先点出来一张角色卡，然后点修改记录」——**看不到卡的历史**。不是误操作，是接错了线：三个面板表面（正文 / 设定 / 大纲）各自持有自己打开的文档，而修改记录页签读的是 **Panel 里那个章节**，卡片的路径从来没有往上报过。没开章时它干脆显示「先打开一章或一张卡」。

修法是把「**作者现在看的是哪份文档**」收到 Panel 一处，由正在前台的那个表面汇报（`active` 为真时才汇报——三个表面都常驻在 DOM 里，一个隐藏的表面认领会把记录从作者脚下换走）。连带三件事：

- **定位也要跟着走。** 点 diff 的一行是「在正文里选中它」，卡片的 diff 行必须落在卡片的编辑器里，不能落进章节缓冲区——那是另一份文档。所以定位请求按 `surface` 路由，三个编辑器各有一个 `textarea` ref。
- **回滚后要让别的编辑器重读。** 回滚是 host 侧的普通写入，不经过卡片/大纲编辑器，它们的缓冲区会继续显示刚被换掉的那段文字，看起来就是「回滚没生效」。加一个 `refreshToken`：变了就重读当前打开的那份文档。
- **顺带把定位算法抽出来测**，于是又抓出一个 P4 时期的真 bug（§4.1c）。

> 这一条是**换了个角度**才发现的：检查脚本只从「章节路径 / 卡片路径」调过历史接口，从没模拟过「在面板里点一张卡，再去看记录」。**脚本能覆盖接口，覆盖不了「谁在什么时机调它」。**

修完之后在真实实例上单独验了一遍卡片的路径（临时探针，已删）：建卡 → 两次保存（第二次带 `source: task`）→ 列表 3 版且来源正确 → 单条 diff 只标出改动的那一行 → 回滚 200 并把卡片正文换回 → 记录 4 版且最新是 `revert` → 同一本书里章节的历史不受影响。

### 4.1c 抽取定位逻辑时，抓出一个 P4 时期的真 bug

「点一行跳转到正文」和 M4 的「定位到正文」是同一件事，所以把选区算法抽成了 `src/client/locate.ts` 的 `findQuote`（纯函数，可测）。抽的过程中被新写的断言当场打脸：

- **注释写着「模型可能漏掉一个标点或换行」，代码却只忽略空白。** 于是引文「陈默握紧了那半块青铜镜指节发白」对上一句正文里带逗号的写法，**一个字都找不到**——正好是这段兜底存在要解决的问题。
- **结尾位置是按引文长度加出来的，不是走出来的。** 引文与它匹配上的原文，在被忽略的那些字符上长度不同，`start + quote.length` 必然短一截（最简情形：正文 `A\nB`、引文 `AB`，选中的是 `A\n`）。M4 起一直如此——滚动用的是起点，所以看着「差不多对」，没人发现。

两处都改了：忽略集合变成「空白 + 标点」，两端都用同一套遍历在原文里定位，三条断言钉住（`format-check` 的「定位到正文」一节）。

**教训不是「抽取能发现 bug」，而是：注释与代码不一致时，两边都得改，而只有测试能告诉你哪边是错的。**

### 4.2 真实实例（HTTP + 真 `ctx.fs`）

在隔离实例上跑完整流程（临时探针，已删）：初始化一本干净的书 → 手写保存 → 采纳「润色本章」后保存 → 列表 → 取单条 diff → 回滚 → 读回。

```
列表 200：3 版
  13:00:51.719Z · update · task(润色本章) · 86→96 字节
  13:00:51.677Z · update · manual        · 142→86 字节
  13:00:51.626Z · create · manual        · 0→142 字节

单条 diff 13 行：
    --- / id / number / status / title / volume      ← 上下文
  - wordCount: 7
  + wordCount: 14
    ---
    陈默走进青石巷。
  + 风从巷口灌进来。

回滚到「润色本章」那一版 → 200
  磁盘上的正文 = "\n陈默走进青石巷。\n风从巷口灌进来。\n"
  记录现在 5 版：revert / revert / update / update / create

边界：不存在的版本 404 novel/not-found · 非文档路径 400 novel/not-a-document ·
      非法动作 400 novel/bad-request · 从没保存过的章 200 且 0 版（不是报错）
```

三件只有真跑才知道的事：**任务来源确实随 HTTP 落到了记录里**；**diff 里的 `wordCount` 变化是对的**（`stampWordCount` 盖的章被如实报出来，而不是被当成噪声藏掉）；**回滚把正文逐字换了回去**。

> **一件环境事实**：本机隔离实例里**覆盖写已存在的文件会被 Windows DACL 拦**（`SetFileSecurityW EACCES`，`06` §3.3 记过）。第一次跑这个探针时，两次 `chapter write` 全部 403，于是列表里只有脚手架那一条 `create`——看起来像「M7 没记录」，实际是**写根本没落盘**。这次我把实例的进程换成了不受文件围栏约束的启动方式，才跑通 update 与回滚。**这解释了为什么探针当时只报「1 版」而不是报错**：探针没有检查写入的状态码。探针也是代码，它错的时候会以产品做错的样子报出来（`07` §3.3 的老账，又犯了一次）。

## 5. 已知欠账

- **记录写入失败时面板不会说。** 保存仍然成功（这是对的），但那一版没记上这件事作者看不到，只有 host 日志里一条 warning。
- **只记面板的写入。** 在 VSCode 里直接改文件不会产生版本——M7 记录的是「面板内的行级历史」，这正是需求划的边界（§1）。相应地，面板外的改动会让「最新一版」与磁盘内容不一致，此时回滚的语义仍然是「回到那一版」，但作者未必知道中间还有别人动过。
- **没有 diff 的并排视图。** 现在是统一的逐行列表（增/删/上下文），不是左右对照。对一章的改动够用，对整本书的改动不够。
- **列表默认只取最近 50 条**，没有翻页，也没有「清空历史」。（清空会需要删除原语，而 `ctx.fs` 没有——真要做得靠存档式降级，见 `03` §4.6。）
- **`Ctrl+Z` 的绑定位置是一处需求偏差**（§2.4），全局快捷键策略留给 P5。
- **面板外的改动不会被记录成一条版本**，所以「这一版之后磁盘被谁改过」在记录里看不出来。
- **「当前看的是哪份文档」靠各表面自报。** 三个表面都常驻 DOM，汇报时机是它们「成为前台」时；如果将来再加一个能编辑文档的表面，它必须同样汇报，否则修改记录会退回今天这个 bug。
- **定位只覆盖有正文 `textarea` 的编辑器。** 大纲页签里「章纲（beats）」那一栏编辑的是 frontmatter 数组、不是正文，所以在那里没有可定位的目标；点 diff 的行会落到大纲编辑器上（如果那一版改的是卷纲）或什么都不选中。
