## 1. 这一期做了什么

需求 M6 明确分两层：**确定性检查（规则）** 和 **模型检查**。这一期做的是第一层，第二层没做（见 §5）。确定性层的产出是一份**可点击定位、每条带双侧依据、可忽略并记住**的报告。

**时间线的两条规则（`timeline-ref` / `timeline-order`）读的是 `src/novel/timeline.ts`**（2026-09-12 抽出来的）——同一份 `parseTimeline` 也是面板「时间线」页签那个逐行编辑器的数据来源。此前解析器是 `checks.ts` 里的一个私函数，而面板只能编辑 Markdown 原文：**编辑器和报告对「这一行是什么」有两套理解**，正是这一期要消掉的那种第二种真相。解析规则没变：只有第一格写着「叙事序」的行才算表头，分隔行不算数据，最后一格里的每个 `c\d{3,}` 都算一次引用，**没有章节 id 的行照样读出来**（编辑器要显示它，规则跳过它）。

### 1.3 一条 issue 由什么组成

| 字段 | 是什么 |
|---|---|
| `key` | **事实的身份**：`规则:路径:目标`。忽略存的就是它 |
| `severity` | `error` / `warn` / `info` |
| `title` | 一句话说清哪里不对 |
| `detail` | 为什么不对、该改哪边，用作者的话写 |
| `path` | **跳转目标**：要动的那个文件 |
| `evidence` | **两侧依据**：引用方与被引用方，各一行 |

`key` 用事实而不是措辞，是「可忽略并记忆」（需求 §8）能成立的前提：改一句提示语不该让作者已经做过的判断复活。检查脚本里有一条断言专门钉这个（同一语料跑两次，key 序列完全一致）。

### 1.4 面板怎么读这份报告

进「检查」页签**自动跑一次**（确定性、快、不用确认），之后只有点「重新检查」才再跑；换一本工程会清空报告并重新检查。

报告按严重度分三段（错误 → 警告 → 提示），每条显示规则名、详情、可展开的「依据 N 条」，右侧两个动作：**跳到第 N 章 / 打开**、**忽略 / 取消忽略**。勾「已忽略 N」能把忽略的展开（半透明）并取消忽略。对不上任何问题的旧忽略记录会被单独提示（`stale`），不会影响结论。

### 1.5 一处落盘偏差：忽略项写 `.novel/checks.json`，不是 `.novel/index.json`

需求 §4 M6 写的是「忽略项写 `.novel/index.json`」。本期**没有照做**，理由是格式真源把那个文件定义成另一种东西：

> `03-project-structure.md` §5：索引永远可重建，所以它不进 git，也不允许成为唯一真相。

把「这条我认了」存进一个可重建、不进 git 的缓存，等于作者的决定会在某次重建后无声消失，而且永远不会被提交、换机器就丢。忽略是**作者的决定**，和 `runs/`、`history/` 同类——所以它拿到自己的文件 `.novel/checks.json`，**进 git**。这条偏差已回写 `03` 的 S6 表与新增的 §4.7。

### 1.6 故意不报的五种情况

误报的代价写在需求 §8（一致性检查误报 → 信任度下降），所以「不确定就不报」是这一层的规矩：

1. **`plannedPayoff` 是散文**（「第一卷末」）：这一层算不出它，就不对「是否逾期」下结论。只有写着真实章节 id、且书已经写到更后面时才报。
2. **空章的字数**：新建的章 `wordCount: 0`、目标 3000，那不是「偏离」而是「还没写」。
3. **存档章占着的章号**：存档不释放章号（格式 §4.6），所以那个号不是缺号。
4. **`firstAppear` 指向不存在的章 vs 与最早登记不一致**：两种说法分开写，不混成一句含糊的「firstAppear 有问题」。
5. **不在工作集里的卡**：命名与生命周期这几条规则只对**还在用的卡**说话——`alias-clash`（名字/别名撞车）、`thread-ref` / `thread-unpaid` / `thread-quote`（伏笔的引用、状态、原句）、`card-ref`（卡片关系）、`firstappear-mismatch` 都不再因为一张退休的卡而开火。退休有两种（格式 §4.4 / §4.6 的两个字段，判断在 `novel/cards.ts`，面板与 host 共用同一份）：
   - **`archived: true`** —— 作者把这张卡删了；
   - **`status: abandoned`** 的伏笔卡 —— 作者把这条线放弃了：线不要了，名字也重新可用。
   **但 id 仍然有效**：`missing-ref` 解析 id 时照样算上退休的卡，所以删一张卡不会让引用它的每一章突然变成「引用不存在的卡」——那种情况由 `archived-ref`（提示，活章 → 存档卡）来说。
   这条是**作者点出来的真 bug**（见 §2.4），而且是连着两次：先「删除」（存档），后「放弃」。
6. **存档章「关于它自己」的规则**（2026-09-12，作者确认后改）：`word-drift`（字数偏离）、`pov-unlisted`（视角人物没登记）、`missing-ref`（它自己的 frontmatter 指向不存在的卡）都**只看活章**；`firstAppear` 的「最早出场」也只在活章里比较——一张撤掉的章不该是那个跟卡片对不上的东西。
   **两处例外，是同一条原则的另一半**：`id-mismatch`（声明的 id 与文件名不一致）与 `chapter-number` / `chapter-gap`（重号与缺号）**照旧把存档章算进去**——存档章的 id 与章号**不释放**（格式 §4.6），它仍是有效的**引用目标**与占号者，所以那里的错会真的影响活文档。§2.5 有实测。

## 2. 三个需要记录的决定

### 2.1 报告按需写，不是每次跑都写

需求说「报告写 `.novel/runs/`」。但 `.novel/runs/` 是**进 git** 的（格式 S6），而检查可以一天点十次——每点一次留一份几百 KB 的报告，会把 AI 任务留痕埋掉。所以：跑检查不写盘，**「保存报告」按钮**才写。这与 D9「不静默改写」同源：写盘这个动作由作者发起。

### 2.2 章节缺号要区分「没人占」和「存档占着」

需求只说「缺号」。但存档章保留 id 与章号（P2 的 `05` §1.7），所以 1..N 之间出现空洞有两种完全不同的原因：作者存档了一章（正常），或者文件在面板之外被删了（真问题）。规则用 `archived` 区分二者，只报后者——**一条会天天误报的规则等于没有这条规则**。

### 2.3 章号重复是错误，`number` 与文件名不一致不是

格式 §3.1：`number` 是显示章号、可以任意改，id 才是不变的身份。所以 `c0003` 写着 `number: 7` 完全合法，不在检查范围内；但两个章都写 `number: 3` 会让「上一章」与阅读顺序失去意义，是错误。**检查的必须是格式的不变量，不是我觉得奇怪的形状。**

### 2.4 「删掉的伏笔还在检查里」——作者报的真 bug，以及它划出的那条线

作者的操作：删掉一条伏笔（面板的「删除」＝`archived: true`），再写一条同名的——检查页立刻报两条 `alias-clash`：一条指着新卡，一条指着那张**已经被删掉**的卡。

原因是这一层把「工程里所有卡」当成了「作者还在用的一组」。而格式 §4.6 早就说清楚存档是**撤出**：面板的卡列表默认不显示它、任务装配过滤它（`client/tasks.ts`）、字数与章数不算它。规则没有跟着做，于是删掉的东西一直回来找你。

**第二次报告把这条线拉长了：他其实是「放弃」，不是「删除」。** 修完存档那一半之后，他又贴来一条 `alias-clash`——两张都叫「test」的卡，其中 `th-001` 是 `status: abandoned`、**没有** `archived` 字段。也就是说：面板上那个叫「放弃」的按钮（`12` §1.1 的第三个入口）写完状态就完事了，而线一旦不要了，它还在抢名字。在真书上量了一遍，比报告里说的还糟：

```
放弃的 th-001 + 活着的 th-002，都叫「test」
修复前：checks 2 条 alias-clash；检索「test 埋在哪」解析出 th-001 与 th-002 两个实体，
        而答案取的是 **放弃的那一个**（「伏笔「test」：abandoned」）——退休的卡悄悄赢了
修复后：checks 0 条；检索只解析出 th-002，答案来自活着的线；th-001 仍作为正文/标题命中出现
```

最后一条尤其说明**为什么不能只把检查关掉**：撞车规则的存在理由是「撞车时只有一个能命中」，而当时确实是退休的那张在命中。所以三处一起改，判断收在 `novel/cards.ts` 的 `isRetiredCard()` 里，面板与 host 共用：`checks.ts`（命名/生命周期规则）、`search.ts`（`resolveEntities` 不再把退休的卡当实体）、`client/tasks.ts`（`renderCast` 不再把放弃的线当可用设定）。伏笔页签仍把放弃的线列在「已废弃」组——那是**记录**，不是可用的线。

现在分成两类（§1.6 第 5 条）：**命名与生命周期**的规则只看活着的卡；**id 解析**仍然对所有卡有效。这条线是有意的，两个方向都有代价：

- 如果按 id 也只看活卡，那么删一张卡会让**每一章**关于它的引用变成 `missing-ref` 错误——删一次弹出几十条错误，是最劝退的一种误报。
- 如果命名规则也看退休卡，就是作者撞到的这个 bug（连着两次）。

两边的取舍落在同一句上：**不要了的东西不该继续对你说话，但它没有从世界上消失。** 恢复那张卡（清掉 `archived`，或把状态改回去），它重新进列表、重新作为实体被解析、重新参与这些规则（都有断言钉住）。

**同一类问题在章节那一侧还开着，本期有意不动**：`word-drift`（字数偏离）与 `pov-unlisted` 现在对**存档章**也会报。按上面的原则，它们大概也该只看活章；但「存档章的字数不重要」这句话没有作者确认，而规则一改就是行为变化。记在这里等一句话（`12` §4 的写法）。

### 2.5 存档章也不再被念叨（作者说「改」之后）

上面那句问话得到了回答：**改**。所以章节这一侧现在和卡片那一侧同源：

| 规则 | 对存档章 |
|---|---|
| `word-drift`（字数偏离） | **不报**——存档章已经不在书稿字数里（`snapshot` 只算活章），「离目标多远」不再是一个关于这本书的事实 |
| `pov-unlisted`（视角人物没登记） | **不报**——`pov`/`characters` 决定**任务装配**带哪些卡，而存档章永远不会被装配进任何任务（`client/tasks.ts`） |
| `missing-ref`（本章 frontmatter 指向不存在的卡） | **不报**——撤出的章不是书稿里的声明；恢复它，这一条就回来 |
| `firstAppear` 的「最早出场」 | **只在活章里比较**——卡片是活的，一张被撤掉的章不该成为和它矛盾的那一方 |
| `id-mismatch`（id 与文件名不一致） | **照旧报**——存档章的 id **不释放**，仍是有效的引用目标（`chapterOf` 解析它），声明错了会让**活文档**的引用落错地方 |
| `chapter-number` / `chapter-gap`（重号 / 缺号） | **照旧算进去**——存档不释放章号，占着的号不是缺号，重号仍是阅读顺序的真歧义 |

实测（隔离实例 + 真 `ctx.fs`，同一个文件只改一个字段）：

```
.chapters/v01/c0900.md —— pov 指向不存在的卡、location 不存在、字数 1 / 目标 3000
  没有 archived          → 5 条：id-mismatch(error) · missing-ref ×2(error) · pov-unlisted(warn) · word-drift(info)
  archived: true        → 1 条：只剩 id-mismatch（外加把 id 也写对之后 → 0 条）
```

顺带一处**检索侧**的同源修正：答案落在**已存档的章**上时（`06` 的「最近一次出场」），现在会明说那一章已经存档、来自被撤出的那一章，而不是把它当成书里的当前位置。命中的**章**仍然照旧出现在命中列表里并带存档标记（M5 的既定行为）——变的只是答案那句话不再撒谎。

### 3.1 每条规则都有正例，关键规则还有反例

`spike/format-check.mjs` 里的语料是**故意摆成每条规则各触发一次**，同时**故意在四处保持安静**：

- 第 2 章没有文件，但有一章存档占着 2 → 缺号只报第 4 章（断言直接钉住 `chapter-gap:...:v1:4`）；
- `plannedPayoff: 第一卷末` 的伏笔 → 一条都不报；
- 空章不报字数偏离；
- 存档章的引用不进 `missing-ref`（卡表里有这张卡）。

另外钉住了：`key` 两次运行完全一致（忽略能活过重跑）、报告按严重度排序、`checkProject` 的 counts 只数**未忽略**的 issue、stale 只装对不上的 key。

host 侧 7 条走内存 `ctx.fs`：`io.check` 在一本只错一处（第 5 章引用已存档的卡）的工程上**只报那一条**（`issues.length === 1`，断言 key 与两处依据）、忽略后离开待处理列表、`.novel/checks.json` 被写出且**只写这一个机器文件**、取消忽略后回来、`saveCheckReport` 写出合法 JSON 且与刚才的报告一致。

### 3.2 写检查脚本时抓到的两件事

1. **渲染检查的 marker 写错了**：我把计数行写成「错误 1」，而界面是「1 错误 · 0 警告 · 0 提示」。这正是那条断言存在的意义——它验的是「这一段真的画出来了」，不是「我以为它长这样」。
2. **内存文件系统的 key 带前导斜杠**：`io` 层写 `.novel/checks.json`，替身里存的是 `/.novel/checks.json`，于是我的 `fs.files.has('.novel/checks.json')` 恒为 false，而旁边那条「不写 index.json」的否定断言则**恒为真**——一个假通过。修法不是改断言语法，而是**换成一个不可能恒真的断言**：列出 `.novel/` 下所有文件，断言里面只有 `checks.json`。替身也是代码，它错了会以产品做错的样子报出来（`05` §3.3 的老账）。
