## 1. 这一期做了什么

需求 M6 明确分两层：**确定性检查（规则）** 和 **模型检查**。这一期做的是第一层，第二层没做（见 §5）。确定性层的产出是一份**可点击定位、每条带双侧依据、可忽略并记住**的报告。

**为什么 `ChecksView` 是纯展示组件**：它原本自己抓数据，那样渲染检查就只能验到「还没检查过」那一屏。把报告交给面板持有之后，渲染检查能喂它一份真报告，于是**报告分支**（分组、依据、跳转按钮）也进了机器判定——这正是 P2 那条「渲染通过 ≠ 分支被执行」的教训。

### 1.3 一条 issue 由什么组成

| 字段 | 是什么 |
|---|---|
| `key` | **事实的身份**：`规则:路径:目标`。忽略存的就是它 |
| `severity` | `error` / `warn` / `info` |
| `title` | 一句话说清哪里不对 |
| `detail` | 为什么不对、该改哪边，用作者的话写 |
| `path` | **跳转目标**：要动的那个文件 |
| `evidence` | **两侧依据**：引用方与被引用方，各一行 |

`key` 用事实而不是措辞，是「可忽略并记忆」（需求 §8）能成立的前提：改一句提示语不该让作者已经做过的判断复活。检查脚本里有一条断言专门钉这个（同一语料跑两次，key 序列完全一致）。

### 1.4 面板怎么读这份报告

进「检查」页签**自动跑一次**（确定性、快、不用确认），之后只有点「重新检查」才再跑；换一本工程会清空报告并重新检查。

报告按严重度分三段（错误 → 警告 → 提示），每条显示规则名、详情、可展开的「依据 N 条」，右侧两个动作：**跳到第 N 章 / 打开**、**忽略 / 取消忽略**。勾「已忽略 N」能把忽略的展开（半透明）并取消忽略。对不上任何问题的旧忽略记录会被单独提示（`stale`），不会影响结论。

### 1.5 一处落盘偏差：忽略项写 `.novel/checks.json`，不是 `.novel/index.json`

需求 §4 M6 写的是「忽略项写 `.novel/index.json`」。本期**没有照做**，理由是格式真源把那个文件定义成另一种东西：

> `03-project-structure.md` §5：索引永远可重建，所以它不进 git，也不允许成为唯一真相。

把「这条我认了」存进一个可重建、不进 git 的缓存，等于作者的决定会在某次重建后无声消失，而且永远不会被提交、换机器就丢。忽略是**作者的决定**，和 `runs/`、`history/` 同类——所以它拿到自己的文件 `.novel/checks.json`，**进 git**。这条偏差已回写 `03` 的 S6 表与新增的 §4.7。

### 1.6 故意不报的四种情况

误报的代价写在需求 §8（一致性检查误报 → 信任度下降），所以「不确定就不报」是这一层的规矩：

1. **`plannedPayoff` 是散文**（「第一卷末」）：这一层算不出它，就不对「是否逾期」下结论。只有写着真实章节 id、且书已经写到更后面时才报。
2. **空章的字数**：新建的章 `wordCount: 0`、目标 3000，那不是「偏离」而是「还没写」。
3. **存档章占着的章号**：存档不释放章号（格式 §4.6），所以那个号不是缺号。
4. **`firstAppear` 指向不存在的章 vs 与最早登记不一致**：两种说法分开写，不混成一句含糊的「firstAppear 有问题」。

## 2. 三个需要记录的决定

### 2.1 报告按需写，不是每次跑都写

需求说「报告写 `.novel/runs/`」。但 `.novel/runs/` 是**进 git** 的（格式 S6），而检查可以一天点十次——每点一次留一份几百 KB 的报告，会把 AI 任务留痕埋掉。所以：跑检查不写盘，**「保存报告」按钮**才写。这与 D9「不静默改写」同源：写盘这个动作由作者发起。

### 2.2 章节缺号要区分「没人占」和「存档占着」

需求只说「缺号」。但存档章保留 id 与章号（P2 的 `05` §1.7），所以 1..N 之间出现空洞有两种完全不同的原因：作者存档了一章（正常），或者文件在面板之外被删了（真问题）。规则用 `archived` 区分二者，只报后者——**一条会天天误报的规则等于没有这条规则**。

### 2.3 章号重复是错误，`number` 与文件名不一致不是

格式 §3.1：`number` 是显示章号、可以任意改，id 才是不变的身份。所以 `c0003` 写着 `number: 7` 完全合法，不在检查范围内；但两个章都写 `number: 3` 会让「上一章」与阅读顺序失去意义，是错误。**检查的必须是格式的不变量，不是我觉得奇怪的形状。**

### 3.1 每条规则都有正例，关键规则还有反例

`spike/format-check.mjs` 里的语料是**故意摆成每条规则各触发一次**，同时**故意在四处保持安静**：

- 第 2 章没有文件，但有一章存档占着 2 → 缺号只报第 4 章（断言直接钉住 `chapter-gap:...:v1:4`）；
- `plannedPayoff: 第一卷末` 的伏笔 → 一条都不报；
- 空章不报字数偏离；
- 存档章的引用不进 `missing-ref`（卡表里有这张卡）。

另外钉住了：`key` 两次运行完全一致（忽略能活过重跑）、报告按严重度排序、`checkProject` 的 counts 只数**未忽略**的 issue、stale 只装对不上的 key。

host 侧 7 条走内存 `ctx.fs`：`io.check` 在一本只错一处（第 5 章引用已存档的卡）的工程上**只报那一条**（`issues.length === 1`，断言 key 与两处依据）、忽略后离开待处理列表、`.novel/checks.json` 被写出且**只写这一个机器文件**、取消忽略后回来、`saveCheckReport` 写出合法 JSON 且与刚才的报告一致。

### 3.2 写检查脚本时抓到的两件事

1. **渲染检查的 marker 写错了**：我把计数行写成「错误 1」，而界面是「1 错误 · 0 警告 · 0 提示」。这正是那条断言存在的意义——它验的是「这一段真的画出来了」，不是「我以为它长这样」。
2. **内存文件系统的 key 带前导斜杠**：`io` 层写 `.novel/checks.json`，替身里存的是 `/.novel/checks.json`，于是我的 `fs.files.has('.novel/checks.json')` 恒为 false，而旁边那条「不写 index.json」的否定断言则**恒为真**——一个假通过。修法不是改断言语法，而是**换成一个不可能恒真的断言**：列出 `.novel/` 下所有文件，断言里面只有 `checks.json`。替身也是代码，它错了会以产品做错的样子报出来（`05` §3.3 的老账）。
